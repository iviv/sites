How a packet finds its way

MeshCore packets are variable length and unusually small. Everything — routing state, addressing, encryption envelope, message text — has to fit in 255 bytes, and the route itself is carried inside the packet as a trail of truncated public keys. Build one below and watch the bytes move.

The header byte

offset 0 · 0bVVPPPPRR

One byte carries three things. Bit 0 is the rightmost bit, so reading the byte left to right you get version, then payload type, then route type — which is the reverse of the order you usually think about them in.

Route type is the first thing a repeater looks at, because it decides the forwarding rule: append yourself and rebroadcast, or check whether you're the next hop. The two TRANSPORT_* variants behave identically but insert four extra bytes after the header — a 16-bit code derived from region scope, and a second reserved code.

Payload version is currently always 0. Version 1 is reserved for a future format with 2-byte source and destination hashes and a 4-byte MAC; it's a growth hinge, not something you set.

The path_length byte

not a byte count
Byte0x02 Hops2 ×1 byte =2 path bytes

This is the field people misread. It is not the length of the path in bytes. The low six bits hold a hop count of 0–63; the top two hold the hash size minus one. The receiver multiplies them to find out how many bytes of path to actually read.

Each hop's entry is the first N bytes of that repeater's Ed25519 public key — a truncated identity fingerprint, not a hash of the route. Since the path field is capped at 64 bytes, hash size and reach trade directly against each other.

With 254 usable one-byte IDs, prefix collisions are inevitable past a few dozen repeaters, and they fail in a way that's hard to diagnose: two repeaters share a prefix, both match the front of a direct-routed path, both strip themselves, and the packet leaves in a direction nobody planned. Multibyte hashes landed in firmware v1.14.0. Repeaters on v1.14.0+ forward all three sizes regardless of their own setting — but older firmware drops 2- and 3-byte packets silently, with no error and no NACK.

Flood once, then go direct

path discovery

MeshCore is hybrid. The first message to a contact floods the mesh and collects breadcrumbs; everything after that follows the learned route hop by hop. Step through it — watch the path field grow on the way out and get consumed on the way back.

What's happening

Flood

Path starts empty. Every repeater that hears the packet checks its seen-table, appends its own hash, and rebroadcasts exactly once. Duplicates arriving later are dropped, so the path that reaches the destination is the trail of whichever copy won the race — not necessarily the shortest one geographically.

Path return

The destination replies with a PAYLOAD_TYPE_PATH packet sent directly along the reversed route. Its payload can carry a piggybacked ACK or response in an extra field, so confirming a message and teaching the sender its route costs one packet instead of two.

Direct

The sender now transmits with the full path prefilled. Each repeater compares only the first hash in the path against its own; on a match it shifts the path left by one hash and retransmits. The path shrinks as the packet travels, which is why a collision on a prefix misroutes so cleanly — and why direct traffic gets forwarding priority with no added delay.

Zero-hop

A path length of 0 means no repeater will forward it. Useful for talking to a neighbour you can hear directly, and for probing local coverage without burning airtime across the whole mesh.

Payload types

header bits 2–5 · pick one

Every multi-byte integer is little-endian. Note that source and destination hashes inside a payload are always one byte in payload version 1, no matter what path hash mode the network is running — the path hash size affects routing only.

Details worth knowing

field notes
  • An ACK has no addressA 4-byte CRC over the message timestamp, text, and sender pubkey. The sender recognises its own message by matching the checksum, so no addressing fields are needed at all.
  • Adverts are the fat ones32-byte public key, 4-byte timestamp, 64-byte signature — 100 bytes before the name or coordinates. This is the heaviest routine traffic on the channel, which is why advert intervals matter more than message rate.
  • Channels are a shared secret, not a networkA group message is addressed by one byte: the first byte of SHA-256 of the channel key. Anyone holding the key decrypts it; anyone who doesn't sees noise with a matching prefix.
  • Long paths cost you wordsEvery hop eats payload budget from the same 255 bytes. At 12 hops in 3-byte mode you've spent 36 bytes on routing before writing a single character. PAYLOAD_TYPE_MULTIPART exists for when that isn't enough.
  • Clients don't repeatCompanion firmware sends and receives but never forwards. Repeating is a deliberate role, which is what keeps flood traffic bounded compared to a mesh where every handset rebroadcasts.
  • Text messages carry a retry counterThe byte after the timestamp packs txt_type in its upper six bits and an attempt number 0–3 in the lower two, so a retransmission is distinguishable from a duplicate.
